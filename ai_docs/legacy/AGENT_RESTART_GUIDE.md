# Руководство по повторному запуску агента-менеджера задач

## Обзор

Этот документ предназначен для агента, который будет управлять задачами проекта SZGMU Bot через todo.txt CLI утилиту. Агент не пишет код, а анализирует задачи, уточняет детали, определяет приоритеты и распределяет задачи между другими агентами.

**ВАЖНО**: Каждый агент должен иметь уникальный ID для идентификации. Система ID агентов описана в `ai_docs/AGENT_IDENTIFICATION_SYSTEM.md`.

## Текущее состояние проекта (на 2025-01-24)

### Архитектура проекта
- **Telegram бот** для управления расписанием СЗГМУ
- **Модульная архитектура** с четким разделением ответственности
- **aiogram 3.x** + **SQLAlchemy 2.0** + **asyncio**
- **База данных**: SQLite (dev) / PostgreSQL (prod)

### Основные компоненты
```
app/
├── bot/                    # Telegram Bot (handlers, keyboards, states)
├── database/              # База данных (models, session, repositories)
├── services/              # Бизнес-логика (15+ сервисов)
├── schedule/              # Работа с расписанием (API client, search)
└── utils/                 # Утилиты (logger, validators, error_monitor)
```

## Текущие критические проблемы

### 1. Ошибки типизации (PRIORITY A)
- **426 ошибок mypy** по всему проекту
- Конфликт модулей: `bot.handlers.start_handler` vs `app.bot.handlers.start_handler`
- Неправильная типизация в сервисах

### 2. Проблемы с группами (PRIORITY A)
- Группы не создаются из расписаний автоматически
- Специальности не сопоставляются с API (код vs название)
- Пользователи не привязываются к группам при выборе

### 3. UI/UX проблемы (PRIORITY A)
- Кнопки с группами не отображаются в интерфейсе
- "Неизвестное действие" при нажатии на факультет
- Callback data слишком длинные (>64 байт)

### 4. Runtime ошибки (PRIORITY B)
- `GroupService` отсутствуют методы: `get_available_faculties`, `find_or_create_group`
- `StudentProfileManager` ошибки в runtime
- `FileNotFoundError` в различных компонентах

## Принципы работы агента

### 1. Анализ задач
- Изучать todo.txt файл регулярно
- Анализировать git status для понимания изменений
- Проверять логи на новые ошибки
- Определять зависимости между задачами

### 2. Приоритизация
- **PRIORITY A (критические)**: Блокируют работу системы
- **PRIORITY B (важные)**: Влияют на UX/функциональность
- **PRIORITY C (желательные)**: Улучшения и интеграции

### 3. Распределение задач
- **Frontend/Bot агент**: UI/UX, handlers, keyboards
- **Backend агент**: Services, database, API
- **QA агент**: Тесты, валидация, документация
- **DevOps агент**: Развертывание, мониторинг, CI/CD

### 4. Контроль качества
- Проверять соответствие CODESTYLE.md
- Контролировать покрытие тестами
- Отслеживать метрики производительности
- Валидировать безопасность

## Структура задач в todo.txt

### Формат записи
```
(A) 2025-01-24 Описание задачи +теги +agent_id:AGENT_ID +контекст @проект
```

**Пример**:
```
(A) 2025-01-24 Исправить ошибку в GroupService +critical +bugfix +agent_id:BE_001_v1 @backend
```

### Теги (tags)
- `+critical` - критические ошибки
- `+ui` / `+ux` - интерфейс пользователя
- `+backend` - серверная логика
- `+database` - работа с БД
- `+api` - внешние API
- `+testing` - тестирование
- `+docs` - документация
- `+security` - безопасность
- `+performance` - производительность

### Контексты (@)
- `@planning` - планирование
- `@features` - новый функционал
- `@technical` - техническая работа
- `@ux_redesign` - переработка UX
- `@code_quality` - качество кода

## Аварийные процедуры

### Если бот не запускается
1. Проверить `BOT_TOKEN` в `.env`
2. Проверить доступность БД
3. Очистить логи и перезапустить
4. Проверить зависимости: `uv sync`

### Если много runtime ошибок
1. Остановить бота
2. Проверить логи в `logs/errors.log`
3. Исправить критические ошибки
4. Запустить с повышенным логированием

### Если БД повреждена
1. Остановить все процессы
2. Восстановить из backup
3. Запустить миграции
4. Проверить целостность данных
