# Feature Specification: SZGMU Schedule Bot Baseline

**Feature Branch**: `001-szgmu-bot-baseline`  
**Created**: 2025-10-10  
**Status**: Draft  
**Input**: User description: "Establish core bot capabilities (schedule search, export, profiles, notifications) from README baseline"

> Спецификация специально увязывает функциональность с принципами конституции: канонические данные расписания (Принцип I), асинхронная оркестрация Telegram (Принцип II), ценность для студента (Принцип III) и тесты до кода (Принцип IV).

## User Scenarios & Testing *(mandatory)*

User stories упорядочены по приоритету, каждая — самостоятельный инкремент, подтверждённый заранее написанными тестами.

### User Story 1 - Просмотр расписания (Priority: P1)

Студент открывает бота, выбирает свою группу/курс и получает расписание на сегодня или неделю с детализацией по занятиям.

**Why this priority**: Без мгновенного доступа к актуальному расписанию бот теряет смысл; все остальные сценарии зависят от этой функциональности и канонической базы данных.

**Independent Test**: Создать и запустить проваливающиеся тесты `tests/integration/bot/test_schedule_commands.py::test_schedule_today_flow` и `tests/unit/services/test_schedule_service.py::test_fetch_day_schedule_returns_canonical_data`, которые обращаются к сервисам из `app/services/schedule.py` и используют фикстуры с загруженными данными в SQLite.

**Acceptance Scenarios**:

1. **Given** студент с настроенной группой и предзагруженным расписанием в БД, **When** он вызывает `/schedule` без параметров, **Then** бот отвечает в порядке времени занятий, используя данные из канонической БД.
2. **Given** студент без выбранной группы, **When** он вызывает `/schedule`, **Then** бот запускает диалог выбора группы, сохраняет выбор в профиле и возвращает корректное расписание из сервиса.

---

### User Story 2 - Экспорт расписания (Priority: P2)

Студент формирует файл расписания на неделю в формате Excel или ICS и получает его в чат.

**Why this priority**: Экспорт повышает удобство, но опирается на стабильную выдачу расписания и те же канонические данные.

**Independent Test**: Добавить проваливающиеся тесты `tests/unit/services/test_export_service.py::test_generate_week_excel_matches_canonical_dataset` и `tests/integration/bot/test_export_commands.py::test_export_week_command_sends_files`, проверяющие, что экспорт пользуется тем же сервисом и БД.

**Acceptance Scenarios**:

1. **Given** валидное расписание группы в БД, **When** студент запрашивает экспорт в Excel, **Then** бот отправляет `.xlsx` с занятиями недели, отражающими текущую БД.
2. **Given** валидное расписание, **When** студент запрашивает экспорт в ICS, **Then** бот выдаёт корректный календарный файл с событиями на основе канонических данных.

---

### User Story 3 - Профиль и уведомления (Priority: P3)

Студент настраивает профиль (группа, формат экспорта, персональные тихие часы) и включает уведомления о предстоящих занятиях.

**Why this priority**: Персонализация и напоминания увеличивают удержание, но строятся на стабильном расписании и экспортных сервисах.

**Independent Test**: Добавить проваливающиеся тесты `tests/unit/services/test_profile_service.py::test_update_preferences_persists_state` и `tests/integration/notifications/test_schedule_notifications.py::test_daily_notification_honors_preferences`, которые подтверждают хранение профиля и использование асинхронных задач.

**Acceptance Scenarios**:

1. **Given** студент без профиля, **When** он проходит настройку, **Then** данные (группа, формат экспорта, интервал тихих часов по умолчанию «выкл») сохраняются и используются при следующих запросах.
2. **Given** включённые уведомления и заданные тихие часы, **When** планировщик обнаруживает занятие, **Then** ассистент отправляет напоминание за пределами запрещённого интервала, уважая предпочтения.

---

### Edge Cases

- Что делать, если внешний источник (API/ICS) возвращает ошибку, таймаут или некорректные данные? Требуются резервные ответы и логирование (Принцип V).
- Как поступать, если у группы нет расписания на выбранный период? Нужно выдавать дружественное сообщение и предлагать альтернативу.
- Как распознаются и разрешаются конфликтующие занятия (пересечения по времени) или противоречия в профиле пользователя?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Бот обязан выдавать расписание только из канонической БД `data/szgmu_bot.db`, взаимодействуя через сервисы в `app/services/` (Принцип I).
- **FR-002**: Команды и меню Telegram реализуются на aiogram 3 с async-хендлерами, без прямых запросов к ORM внутри обработчиков (Принцип II).
- **FR-003**: Экспортные сервисы в `app/schedule/exports/` обязаны использовать те же модели, что и выдача расписания, без копирования логики (Принцип I).
- **FR-004**: Профиль пользователя (группа, формат экспорта, уведомления) хранится и учитывается в каждой ветке обработки (Принцип III).
- **FR-005**: При сбоях внешних сервисов бот вывешивает локализованные сообщения и пишет структурированные логи с корреляционными ID (Принцип V).
- **FR-006**: Перед реализацией функций создаются и падают автоматические тесты (unit + integration), отмеченные маркерами `unit` и `integration` (Принцип IV).
- **FR-007**: Все внешние HTTP-вызовы выполняются асинхронным клиентом `httpx` с заранее заданными таймаутами, ретраями и логированием ошибок; переход на иной клиент допускается только через изменение конституции/плана.
- **FR-008**: Уведомления по умолчанию не отправляются в «тихие часы»; пользователь может настроить индивидуальный интервал в профиле. Система обязана уважать настройки и хранить их в БД (Принцип III).
- **FR-009**: Ингест расписания использует официальный сайт с PDF/таблицами как основной источник, приводя данные к формату legacy CSV; неофициальный API применяется как резервный фид. Любое расхождение между источниками фиксируется в логах и мониторится (Принцип I, V).
- **FR-010**: Изменения схемы данных сопровождаются миграциями или seed-скриптами в `data/`, а отклонения фиксируются в Complexity Tracking плана.
- **FR-011**: Данные о преподавателях и аудиториях нормализуются в отдельных сущностях (таблицы `Lecturer`, `Room`), а уроки (`ScheduleLesson`) ссылаются на них по внешним ключам.
- **FR-012**: Записи `ExportRequest` и `NotificationJob` удерживаются только до завершения операции; после успешного выполнения они удаляются, чтобы не накапливать историю.

### Архитектурные вводные

- **Стек**: Python 3.14, aiogram 3, SQLAlchemy 2.0, Pydantic, Loguru, async HTTP клиент `httpx`. Управление зависимостями — `uv`.
- **Слои**: `app/bot` (хендлеры), `app/services` (бизнес-логика), `app/schedule` (ингест и экспорт), `app/database` (ORM), `app/utils` (общие функции).
- **Данные**: Единственный источник для рантайма — SQLite с миграциями/сидерами; первичное наполнение поступает с официального сайта (PDF/таблицы, приводимые к CSV), резервное — из неофициального API для сверки и backfill. Преподаватели и аудитории хранятся в таблицах `Lecturer` и `Room`, `ScheduleLesson` содержит внешние ключи.
- **Инфраструктура качества**: Обязательные команды `uv run ruff format .`, `uv run ruff check .`, `uv run mypy app`, `uv run pytest` выполняются до ревью.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% запросов `/schedule` для кэшированных групп отвечают за <3 секунд (замер на стенде с логированием).
- **SC-002**: 100% экспортов формируют корректные `.xlsx`/`.ics`, что подтверждено автоматическими тестами и проверкой контрольных файлов.
- **SC-003**: 90% уведомлений доставляются без ошибок в течение 7-дневного тестового периода; сбои логируются и анализируются.
- **SC-004**: CI проходит `ruff`, `mypy`, `pytest` без пропусков; покрытие новых модулей ≥80%.
- **SC-005**: При отказах внешних сервисов пользователи получают локализованное сообщение без утечки внутренних деталей, а инциденты фиксируются в логах.
