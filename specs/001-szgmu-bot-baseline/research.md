# Phase 0 Research: SZGMU Schedule Bot Baseline

**Date**: 2025-10-10  
**Owner**: Project Architect

## Objectives

- Зафиксировать текущий контекст: источники данных расписания, готовность сервисного слоя, инфраструктура тестирования.
- Определить риски и неизвестные перед началом планирования и разработки.
- Подготовить входные артефакты для data-model и plan обновлений.

## Findings

### Schedule Data Sources
- Официальный сайт публикует PDF/таблицы, совместимые по структуре с legacy CSV. Необходимо автоматизировать парсинг PDF → структурированные таблицы (модуль `app/schedule/ingest`).
- Неофициальный API обновляется реже; подходит как резервный источник для backfill и сверки. Требуется документировать его эндпоинты и ограничения (rate limits, доступность).
- Legacy-скрипты в `legacy/` можно использовать как начальную точку, но код необходимо переписать под текущую архитектуру и Python 3.14.

### Service Layer & Architecture
- `app/services/` содержит базовый набор сервисов, но отсутствует унифицированный интерфейс для экспорта и уведомлений. Потребуется дизайн новых методов/классов с общими контрактами для aiogram-хендлеров и фоновых задач.
- `app/bot/handlers/` реализует часть команд. Требуется рефакторинг для разделения логики и внедрения новых сценариев без прямого доступа к БД.
- Асинхронные задачи (уведомления) пока реализованы частично; нужно подтвердить используемый планировщик (например, APScheduler) и совместимость с текущим циклом событий.
- Модели преподавателей и аудиторий придётся нормализовать (отдельные таблицы `Lecturer`, `Room`) и обновить сервисы/ингест под новые внешние ключи.

### Testing & Quality
- Тестовая структура (`tests/unit/`, `tests/integration/`, smoke) существует, но покрытие по данным сценариям ограничено. Необходимо добавить фикстуры расписаний и профилей.
- Настроены `ruff`, `mypy`, `pytest`; переход на Python 3.14 потребует проверки конфигов (`pyproject.toml`, `mypy.ini`).
- Отсутствует стратегия тестирования парсинга PDF; потребуется либо мокирование, либо хранение эталонных файлов в `tests/fixtures/files/`.

### Tooling & Dev Experience
- Используем `uv` для зависимостей. Надо проверить готовность пакетов aiogram/SQLAlchemy к Python 3.14 и при необходимости зафиксировать версии.
- Логирование через Loguru настроено, но нет стандартизированных correlation IDs; нужно добавить утилиту в `app/utils/logging.py`.
- Команды CLI (`create_groups.py`, `init_database_data.py`) устарели; оценить, какие из них следует переписать или удалить.
- Для тихих часов храним только текущее значение в `UserProfile`; история не требуется.
- Записи `ExportRequest`/`NotificationJob` удаляются сразу после успешной завершения, поэтому необходимы логи и метрики для диагностики.

## Risks & Unknowns

| Риск | Вероятность | Влияние | Митигирующие действия |
|------|-------------|---------|------------------------|
| PDF-парсер не извлекает корректную структуру | Средняя | Высокое | Прототипировать парсер на примере; хранить тестовые PDF; рассмотреть сторонние библиотеки (camelot/Tabula) |
| Неофициальный API недоступен | Высокая | Среднее | Сохранить data snapshot; настроить мониторинг и алертинг; автоматизировать fallback на PDF |
| Асинхронный планировщик конфликтует с aiogram | Средняя | Среднее | Проверить совместимость выбранного scheduler (например, APScheduler async); протестировать в отдельном окружении |
| Переход на Python 3.14 ломает зависимости | Средняя | Высокое | Провести smoke-тесты зависимостей, обновить lock-файл, добавить в CI matrix |
| Недостаток покрытия тестами | Высокая | Высокое | Создать план тестов на фазе tasks; обеспечить failing tests до разработки |
